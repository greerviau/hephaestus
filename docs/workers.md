# Workers

A worker is a linked T3 environment that the owner marked on the Workers page. Hephaestus sets each worker up through short T3 threads on the owner's own provider instance (`factory.setup` in the config), so the owner only signs the factory instances in.

1. Name a private config repo at the top of the Config page, such as `owner/hephaestus-config`. On the first deploy Hephaestus creates it, private, with `gh` when GitHub says it does not exist, and it refuses a repo that is not private. It pushes one tag per deployed version, named with this install's id, from a clone in `~/.hephaestus/config-repo`. Each worker needs `gh` signed in to an account that can read the repo; the deploy script uses it as git's credential helper.
2. On the Workers page, open the machine's row and click Use as a worker. Approving a version on Config deploys it to every worker, and Deploy config on a worker retries. The deploy thread sends `templates/worker/deploy.sh` inline. The script fetches the version's tag, checks that its commit holds that version, installs it under `~/.hephaestus/` on the worker, and adds the Factory Claude (`hephaestus-claude`) and Factory Codex (`hephaestus-codex`) provider instances to T3's `settings.json`, changing no other setting. Writes to that file hold a lock and start over if T3 changed the file meanwhile. The script also keeps the owner's `~/.claude/CLAUDE.md` and `~/.agents/skills` out of factory threads. Hephaestus checks that the worker reports the commit it published.
3. Click Sign in Claude, then Start sign-in on the page that opens. Open the thread "Hephaestus: sign in Factory Claude" on that worker in T3 and paste the token that `claude setup-token` prints into its secret prompt. The same token works on every worker.
4. Click Sign in Codex. The worker's row shows a link and a code; approve the code in a browser within 15 minutes.
5. After each deploy and sign-in, Hephaestus runs a one-line test turn on each factory instance. The worker is ready once it runs the deployed version and commit, its last deploy succeeded, both test turns since that deploy passed, and T3 reports no problem with either instance. A test turn that stops on the provider's usage limit says nothing about the sign-in: the worker waits, and the turn runs again a minute after the reset time T3 gives the snoozed thread, or after 30 minutes when T3 gives none. The setup checklist on Home counts the worker signed in meanwhile, and Home says which instance reached its usage limit.

A worker that is running factory threads gets a new version only after they finish, so a thread never sees instructions or skills change under it; it takes no new threads meanwhile. A failed deploy is retried after 30 minutes, and every worker is deployed again every 6 hours so owner skills added since stay out of Factory Codex. A worker is also deployed again after it clones a project that loads skills of its own, so the clone gets the hook that gives the project's threads those skills (see [The factory](factory.md)). A launch whose reply from T3 was lost is replayed with the same request id. T3 scopes that id to Hephaestus's T3 session, and a sign-in change opens a new one, so before a replay Hephaestus lists the worker's threads with exactly the launch's title and adopts the newest one no other launch has claimed. When T3 cannot list them, the launch is not replayed and is tried again later. At startup, every launch an earlier run left unanswered is adopted the same way, or marked failed when T3 has no thread for it. A task that stalls is given up after a timeout. T3 writes its `settings.json` with its own writer, which Hephaestus cannot lock: the deploy script checks the file just before replacing it, so only a T3 write in the moment between that check and the rename could be lost.

Uninstall stops the service, waits until T3 lists no Hephaestus setup thread as running on each worker, and then runs a cleanup thread there that signs the factory Codex out, removes both instances, and deletes `~/.hephaestus/`. If the logout or the instance removal fails, `~/.hephaestus/` stays on the worker so the cleanup can run again. If any worker cannot be cleaned up, uninstall changes nothing on this host, starts the service again, and names the workers; `uninstall --skip-workers` removes Hephaestus anyway. Revoke the Claude setup token in your Claude account afterwards.
