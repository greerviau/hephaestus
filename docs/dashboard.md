# Dashboard

The dashboard is a set of server-rendered pages behind the dashboard password. It works without JavaScript: every owner action is a plain form that posts and returns to the page, and dialogs and the "..." menus are HTML popovers and `details` elements. The one script, which keeps live pages current, is optional.

The pages follow the browser's light or dark setting. Links to GitHub open in a new tab. The pages, the agents, and the T3 threads all call a unit of work a task, as in the `task_id` argument of an agent's tool call.

## Sidebar

Every page has the same sidebar. It lists the pages in two groups: Factory (Home, Work, Activity, Analytics) and Setup (Projects, Workers, Chat, Proposals, Config). Home carries a count of what needs you, and Proposals a count of the proposals that wait. The count on Home covers every project and leaves out T3 links that are about to expire, which only Home itself reads. At the foot, the sidebar says whether the factory is running or paused, with a Pause button that asks first and a Resume button that does not, the commit the service runs, how many new commits `origin/main` has and a link to the Update page that runs the update (see [Install](install.md#update)), the config deploy status, and Sign out. The deploy status appears while a deploy runs, with the version and how many more wait, and after it ends: a success shows for 30 seconds, and a failure stays until a later deploy ends, with a link to the version to deploy it again. The service log has the error text. While a deploy runs, every page refreshes itself every 3 seconds so the status stays current. On a narrow screen a Menu button opens the sidebar.

While `origin/main` has new commits, every page except Update opens with an Update available notice. It has an Update now button that starts the update, or, when the service cannot update itself, the command to run on the Hermes host. While an update runs, from the dashboard or a shell, the notice says so and links to the Update page.

The Project picker at the top of the sidebar lists the factory's projects. Choosing one and pressing Apply stores the choice in a cookie for a year, and "All projects" clears it. A choice that names a repo that is no longer a factory project is ignored. The picker narrows Home, Work, Activity, and Analytics, and no other page.

## Reloading

Pages that show live status refresh themselves. A small script, served at `/assets/live.js`, fetches the page's own address again, so the tab, view, filters, and an open Workers row stay, and swaps in only the main region and the sidebar when their content changed. The page and the sidebar keep their scroll positions, and open `details` menus stay open. The script waits while a field has focus, a dialog or popover is open, or the tab is hidden, and tries again after a failed fetch. It reloads the page when the session has ended. A browser that runs no scripts reloads the whole page with a meta refresh instead, and that reload discards typed text and closes an open dialog. Either way the address is loaded without the `notice` parameter, so the banner that reports an action's result shows once.

The table below gives how often each page refreshes.

| Page                                                 | Refreshes                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------- |
| Home (`/`)                                           | Every 10 seconds; every 5 while T3 has not answered           |
| Work (`/work`), every tab, as a list or a board      | Every 10 seconds                                              |
| A task (`/work/<id>`)                                | Every 10 seconds                                              |
| A thread's transcript (`/threads/<worker>/<thread>`) | Every 10 seconds while the thread runs; not once it has ended |
| Activity (`/activity`)                               | Every 10 seconds                                              |
| Workers (`/workers`)                                 | Every 10 seconds; every 5 while T3 has not answered           |
| Planning and chat model (`/config/models/planning`)  | Every 5 seconds, only while it waits on a sign-in code        |
| Every other page                                     | Never                                                         |

A reload discards typed text and closes an open dialog, so no reloading page holds a field to type in. The forms reached from those pages are pages of their own that do not reload: Request work (`/work/new`), Send to lead (`/work/<id>/lead`), Abandon (`/work/<id>/abandon`), and Sign in Claude (`/workers/<id>/sign-in-claude`). The planning and chat model page leaves out its model field while it waits on a sign-in code. A confirm with nothing to type stays a dialog on the reloading page.

## Home

"Needs you" on Home is one list. It holds tasks escalated to you, issues waiting for admission (including issues held by a project's cap), proposals, T3 links that expire within 7 days, workers whose next step is yours, and notifications you have not dismissed. Each row names its kind and has one main action; a task's other actions are in its "..." menu. A task's main action is the merge to approve, or Send to lead when it waits on no merge. An issue's row shows its number and title as a link to the issue on GitHub, with its repo and why it waits underneath.

The Project picker narrows Home's tasks and issues to the chosen project, and leaves out a notification about another project's task, as Activity does. Proposals, workers, T3 links, and notifications about no task stay. Home shows a box with a Resume button while the factory is paused. While a setup step is left, the page is titled "Set up the factory", and the lists appear under the steps only once one of them has a row.

## Work

Work is at `/work` and opens on In progress. Needs you (`/work?tab=needs`) holds the tasks escalated to you and the issues waiting for admission, with the rejected issues folded under them. Their rows and actions are the same as on Home. In progress leaves out the tasks that wait for you. Its board (`/work?view=board`) has a lane for each stage that holds a task: Admitted, Implementing, Reviewing, Testing, Merging, Verifying, and Reverting, and one for tasks with the lead. Under the lanes it names the stages that hold none. Above the list or board, a line says how many factory threads run against the limits, and a box says why no thread starts while the factory is paused or at a limit.

Request work opens a form at `/work/new`. The request is filed as a GitHub issue. It is factory-filed, so it is admitted at once unless the project already has its cap of factory-filed issues waiting for work; then it waits for you like any other held issue. Sending a task to the lead and abandoning one are forms on pages of their own too. Each of the three takes a `back` address, a path inside the dashboard, and returns there once the form is accepted. A field the server refuses is marked under the field, and a request GitHub refuses comes back with what you typed.

A request's title takes 256 characters and its details 10,000; a note for the lead and a reason to abandon take 2,000 each. Each form reads enough bytes for its fields at those limits in any script. A form larger than that is answered as too long, with the limits, and changes nothing. The buttons that take no typed text return with a notice that the form was too large.

### Stage names

The pages name a task's stage by the seven steps of the task page's tracker: Admitted, Implementing, Reviewing, Testing, Merging, Verifying, and Done. Testing and Merging are both the internal Merging stage, and Verifying is the internal Validating stage. The Work list, the board, Home, and Activity use the same names. A task with the lead, one that needs you, one that is reverting a merge, and an abandoned one are named for that state instead.

Hephaestus does not store check results, so the pages tell Testing from Merging by the reason the merge gate recorded for waiting or escalating. The stage is Merging when the reason is one the gate or the merge step gives only after the head commit's checks passed, and Testing for any other reason or none. The gate and the merge step export those reasons, and the pages read them from there. A task at the gate is read from why it waits. An escalated task is read from the reason its escalation recorded in the task's history, and an abandoned one from the gate's last wait or the escalation it was abandoned from, so a note to the lead or a reason to abandon does not move the task to another step. A task whose checks pass and that merges in the same pass goes from Testing straight to Verifying. Activity and a task's history name the move into the internal Merging stage "Moved to Testing", because a task enters it before its checks pass.

### A task's page

A task's page is at `/work/<id>`. Its tracker shows the seven steps. A task that is reverting a merge stays at Verifying, and an escalated or abandoned task is shown at the step it left.

When a task was sent back to Implementing, the tracker marks how often, and an Attempts section lists each time with the reason the pipeline recorded: the reviewer asked for changes, or the PR conflicted with its base branch. The count starts over when the lead restarts the work or a revert merges, as the pipeline's own count does. Proof appears once the task has a PR. It shows whether the other provider approved the head commit, and how the checks on the merge commit ended, with the names of the checks Hephaestus expects there. The checks read Not started before a merge, Running while the task is at Verifying, Passed once it is done, and Not checked for a merge made outside Hephaestus. They read Failed while the merge is being reverted, and when the task escalated because they failed under a policy that does not revert. Only what the task recorded since its current merge counts, so a task that was reverted and then merged again reads by its second merge. The results of single checks and the implementer's evidence files are on GitHub, not in Hephaestus, so the page does not list them.

Each thread of the task links to its transcript, as Hephaestus recorded it. The task's page and the transcript name a worker by its label, or by its T3 environment ID when Hephaestus has no label for it. The history shows each commit by the first seven characters of its SHA, with the full SHA as the hover text.

## Activity

Activity is at `/activity`. A task's events and notifications belong to its project. An agent call belongs to the project its `repo` argument names, or else the project of the task its `task_id` argument names; a call that names neither shows only for all projects. The store applies the project and role filters before it takes the newest 200 rows of each kind, so a quiet project shows its own newest rows. Dismissing a notification returns to the same view, with a banner that says it was dismissed.

## Projects

A project's page is at `/projects/<owner>/<repo>`. It offers the three presets as choices, and under "Customize the preset" each setting with what every preset sets it to. A form built on an older config version is refused and comes back showing the policy in force.

## Workers

Workers is at `/workers`. A row opens to show the machine's details and actions. Rows that need attention start open: a worker that is not ready, a T3 link that expires within 7 days, and every row while no machine is a worker yet. Clicking a machine's name puts it in the address (`/workers?open=<id>`), which keeps that row open across reloads; an action returns to the same address. While a Codex sign-in waits, the row shows the link and the code to approve. Sign in Claude opens a page with the steps and a Start sign-in button; the token itself is pasted in T3. Stop using as a worker asks first.

## Config

Config is at `/config`. The config repo sits above the tabs on every tab: its name with a Change dialog, or, while none is named, a warning that holds the form. Each form on the Factory, Models, and Agents tabs carries the version it was built from and is refused when the config changed since. The JSON tab does not refuse: it saves a draft built from the version the page was loaded with, and a draft that was not built from the deployed version cannot be deployed. A save creates a config version, approves it, and starts its deploy in the background, unless Deploy now is unticked; then the version stays a draft and its page opens. The save answers at once and returns to the form, which says which version is deploying; the sidebar shows how the deploy ends. Deploys run one at a time, and a version that is already deploying or waiting is not queued again. Approve, Deploy, and a proposal's Approve on the Versions and Proposals pages also answer at once.

- Factory (`/config`) sets the thread limits, the minutes before Hephaestus starts a task the lead has not started, and each role's schedules.
- Models (`/config/models`) has one row per job. Implement is the Factory Claude model, Review is the Factory Codex model, and Housekeeping is the setup model with the T3 provider instance it runs on; the provider of Implement and Review is fixed. Each job's provider options are in a fold. The tab renders at once. "Plan, brief, and chat" shows a loading line first, then fills in the model the factory's Hermes uses and whether its provider is signed in, while you are on the page, because asking Hermes takes seconds. The server keeps Hermes's answer for a minute, the browser keeps the last answer for the tab session and shows it while a fresh one loads, and a failed load shows an error in that row with a Retry button. A Refresh button reads again, and saving on the planning model page drops both copies. The row links to `/config/models/planning`, which sets the provider, signs in, and sets the model (see [Hermes](hermes.md)). That page saves on its own, outside config versions.
- Agents (`/config/agents`) lists four instruction sets and the skills. Planner, Lead, and Improver are each role's `persona` and `skills`; Coding threads is `instructions.factory` and `factory.threadSkills`. An instruction set's page (`/config/agents/<name>`) edits its text and ticks the skills it loads. Each page shows the shipped instructions, folded and read-only, and edits the owner's instructions: for a role they follow the shipped ones, and for coding threads they are the threads' standing instructions on each worker. When the owner's text repeats shipped instructions, the page says how many passages do. A skill's page (`/config/skills/<name>`) edits one file at a time. Add file opens an empty editor on a new path, and the file exists once its text is saved. Rename changes the skill's name everywhere it is loaded and in the `name` line of its `SKILL.md`. Delete removes the skill and unloads it from every instruction set that loads it. New skill creates a skill whose `SKILL.md` carries the name and description. Each of these creates a config version, with the "What changed" text as its message. An editor form built on an older version comes back with the text and skills the current version saved, so saving it again cannot undo the newer change; what you typed is shown under the form, read-only, to copy from. One file or instruction set holds at most 256 KB of text. A file's path cannot lie inside another file of the skill, such as `SKILL.md/notes.md`, and the config refuses such a path on the JSON tab too.
- Versions (`/config/versions`) lists the newest 20 versions, with the rest on request. A version's page (`/config/versions/<id>`) shows its changes as diffs and, folded, the whole config. Approve, Reject, Revert, and Deploy each ask first.
- JSON (`/config/json`) edits the whole config as JSON, for changes the other tabs do not cover, and saves it as a draft.

## Errors

A page that cannot read Hephaestus's store shows an error banner and leaves out the actions that depend on the missing data. The Config tabs are the exception: they answer a store error with a plain "Internal error" response. When T3 or GitHub fails, the page shows a short reason, such as an error code, and the service log has the full error. When T3 has not answered within 2 seconds, the parts of the page that need T3 show as loading until it answers.
