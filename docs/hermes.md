# Factory Hermes

Deploying a version also applies it to the factory Hermes root. The factory's planner, lead, and improver run as Hermes profiles in a Hermes root of their own, `~/.hephaestus/hermes/`, never in the owner's `~/.hermes`. With the factory under the owner's home, the owner's running gateway rewrites the owner's `config.yaml`, and the two gateways run each other's cards and cron jobs (see the Hermes prototype in issue #4).

```sh
node dist/cli.js hermes sync
```

`hermes sync` runs every `hermes` command with `HERMES_HOME` set to the factory root. It makes these changes:

- It turns off model-driven triage and Hermes's own review dispatch, so cards move only through Hephaestus.
- It creates the factory board.
- It brings each role's profile in line with the current config version: the role's instructions (the shipped ones, then the owner's persona; see [Configuration](configuration.md)) and its skills arrive as a profile distribution, and the Hephaestus MCP entry and the role's cron jobs are set through the CLI. The `terminal`, `code_execution`, and `cronjob` toolsets are off, because a cron job can run a script. Tool-progress messages are off too, a reply to a message sent mid-turn does not name the running tool, and a long turn's heartbeat says only that it is working, so the chat does not show the factory's tool names. A per-platform `display.platforms` override in a profile's `config.yaml` would still win.
- It installs and enables the `hephaestus` Hermes plugin in the factory root, which the planning model page uses, and which moves a card out of `triage` (see below).
- It installs and starts `hephaestus-hermes-gateway.service`, the factory's own gateway, which serves only the factory profiles and the factory board.

Install records the `hermes` CLI's path; `--hermes <path>` overrides it. Hermes must run as the same user as Hephaestus, because Hephaestus reads and prunes files Hermes writes in the factory root. Hermes commands also get `HERMES_KANBAN_HOME` set to the factory root, so an inherited value cannot point the factory board at the owner's boards. Set the factory's model on the planning model page, which the Models tab of Config links to as Planning and chat. It lists every provider Hermes supports, with Hermes's own model list for each. A provider that takes an API key gets a key field, and Anthropic's also takes a `claude setup-token` token. A provider with a device-code sign-in (Nous, Codex, xAI, and MiniMax) gets a Sign in button that shows a link and a code. A provider that signs in another way shows the command to run on the host: its own `hermes auth add` command for an external OAuth sign-in, or `hermes model` for one such as AWS Bedrock. The custom provider takes an OpenAI-compatible endpoint URL and an optional key. Hermes checks the model in the factory root and every profile before anything is written; a refusal changes nothing, a refusal while writing says which parts were saved, and a warning, such as a model the provider does not list, saves only when the owner ticks Use it anyway. Each change applies to the factory root and all three role profiles, and then restarts the factory gateway.

The page runs `hermes hephaestus <action>` against the factory root. `hermes sync` installs and enables that action as a Hermes plugin in the factory root only (`templates/hermes/plugin/hephaestus/`), so the owner's own Hermes never loads it. The plugin calls the same Hermes code as Hermes's own dashboard: its model catalog, its credential save, its device-code sign-in, and its model assignment. A key goes to the root's and each profile's `.env`, because a profile reads only its own, and an Anthropic API key and setup-token replace each other; a device-code sign-in goes to the root's `auth.json`, which profiles read. Keys and endpoint URLs reach the plugin on stdin, never on a command line. The page never shows a key again, and an endpoint URL that holds a user name or password is treated the same way: when Hermes warns or refuses, the form comes back without the URL and asks for it again, and the user name, password, and key are cut from the message the page shows. The plugin reports a refusal, a partial save, a warning, or missing Hermes code as JSON on stdout. The page waits for a deploy until the plugin and all three profiles exist. If an update renames the Hermes code the plugin calls, the page says Hermes did not answer as expected; `HERMES_HOME=~/.hephaestus/hermes hermes model` on the host still works then, followed by a deploy so each profile without a model gets the root's. The setup checklist on Home counts the step done once the root and every profile name a model. The MCP entry points at the Hephaestus MCP server on the port after the dashboard's (see [The factory](factory.md#mcp-server)).

Card stages map onto the board this way: Admitted is `ready` for the lead, the stages that run in T3 threads are `scheduled` with the stage in a comment, Done is `done`, and Abandoned is archived. A card escalated to the lead goes back to `ready` with a comment that gives the reason, or to `todo` while a parent card the lead linked is unfinished, and Hermes readies it when the parent is done. Hephaestus parks cards as `scheduled` rather than `blocked` because Hermes sends a task blocked again after an unblock to `triage`, and nothing picks a task up there. Hephaestus parks the lead's task before a card the lead restarts goes back to its implement thread, so the lead's run cannot leave the task where a hand-back cannot reach it. A card the lead's own blocks sent to `triage` still moves: when Hephaestus hands it back or parks it, the plugin's `move-task` action moves it through Hermes's kanban code, the way a drag on Hermes's dashboard does, since Hermes's CLI has no command for that which does not run a model. Hermes completes nothing from `scheduled` or `triage`, so for Done the plugin first moves the task to `blocked`, which no worker claims, and Hephaestus then completes it. Cards complete without Hermes PR completion contracts, which need branch protection; Hephaestus checks CI itself.

## Chat

The Chat page connects Hephaestus to Discord or Telegram. Make a bot for the factory alone: a bot whose token another Hermes gateway also uses would have its messages taken by both. Hephaestus writes the bot's token, the allowed user IDs, and the chat to the `.env` of the factory profile that talks to the owner, which only the owner can read, and restarts the factory gateway, which then runs the bot. The token is never shown again, never stored in a config version, and never passed on a command line.

On Discord, the channel you give is a request channel: the bot answers there without an @mention and opens a thread for each request. On Telegram, requests and replies use your direct chat with the bot, or a group you name.

With alerts on, Hephaestus posts each new notification, the items that appear under Needs you, to the chat with a link to the dashboard. Alerts start from the moment you turn them on, so earlier notifications are not sent.

### Requests and their threads

When you ask for work in the request channel, the factory files the issue and replies in the request's thread with the issue's link and a line such as `Tracking you/your-repo#12`. Hephaestus looks for that line, in messages from the bot only, in the channel's active threads every 30 seconds. From then on it posts the work's milestones in that thread: work started, PR opened, the review's result, merged, checks passed on the default branch, reverted, stopped, and anything that needs you, with a link to the card.

When the change can be seen, the engineer saves screenshots, a recording, or output files and pushes them to `refs/hephaestus/evidence/<install>-card-<id>`, a ref that holds only those files and is not a branch. When the PR opens, when the work is done, and when a thread starts following a card that is in review, merging, merged, or done, Hephaestus downloads up to six files of up to 8 MB each from GitHub and attaches them in the thread, once per set of files.

Threads and progress work on Discord. On Telegram, requests and replies use your chat with the bot, and alerts reach you there, but Hephaestus does not follow a request's progress.
