# Configuration

All factory config lives as numbered versions in `~/.hephaestus/state.db`: factory projects and their policies, the planner, lead, and improver roles, the instructions for factory threads, and skills. No repo holds them.

- Every edit creates a draft version with a diff against the version it was built from: the deployed version, or before the first deploy the newest approved one. A draft becomes approved or rejected, an approved version becomes deployed, and the version it replaces becomes superseded. Only a version built from the deployed version can be deployed, so deploying never drops changes made in between.
- Reverting a deployed version creates a draft that restores what that version changed. A change stays as it is when a later version changed the same value, or when undoing it alone would make the config invalid, and the page says how many such changes it left. The first version cannot be reverted.
- A project's policy starts from a preset, `standard` when none is given, and can override any setting. `yolo` merges when checks pass, with no review and no escalation paths. `standard`, the default, also needs an approving review from a different provider on the head commit and stops for changes under `.github/workflows/`. `strict` makes every merge wait for the owner. All three revert a factory merge whose checks fail, allow 2 review rounds, cap open factory-filed issues at 5, and need checks to run on a PR; `allowNoChecks` lets a repo without CI merge without them, and `requiredChecks` names checks that must pass on the head and on the merge commit: a bare name is a check run, and `status:<context>` is a commit status.
- Each role's own instructions ship with Hephaestus in `templates/roles/`, and no config version holds them, so the owner cannot edit them and an update brings new ones. A role's `persona` holds only the owner's instructions, which the role gets after the shipped ones under the heading "The owner's instructions"; it starts empty. Install once copied the shipped text into version 1, so a persona can hold a copy of an older build's instructions: a paragraph that matches one any build shipped is left out, and the Agents page says how many it left out. When the service starts and the shipped instructions differ from the ones the factory Hermes root last got, Hephaestus applies the current version to the root again.
- The Config page edits the config by tab, and every save creates a version (see [Dashboard](dashboard.md)). Its Versions tab lists versions with their author and state, and a version's page shows its diff and can approve, reject, revert, and deploy it. Deploying publishes the version to the config repo, applies it to the factory Hermes root, and starts a deploy thread on every worker (see [Workers](workers.md)).
- The `factory` section sets which skills factory threads load (`threadSkills`), the model for each factory instance, the owner's own instance and model that run setup threads on a worker, and the thread limits.
- Every night at 03:00, Hephaestus writes all versions to `~/.hephaestus/backups/` and keeps the newest 14 backups.
- `~/.hephaestus/secrets.json` (mode 600) holds named secrets that config versions refer to by name. Backups leave it out, so secrets must be entered again after a restore.
