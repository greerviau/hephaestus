# Configuration

All factory config lives as numbered versions in `~/.hephaestus/state.db`: factory projects and their policies, the communicator, lead, and improver roles, the instructions for factory threads, and skills. No repo holds them.

- Every edit creates a draft version with a diff against the version it was built from: the deployed version, or before the first deploy the newest approved one. A draft becomes approved or rejected, an approved version becomes deployed, and the version it replaces becomes superseded. Only a version built from the deployed version can be deployed, so deploying never drops changes made in between.
- Reverting a deployed version creates a draft that restores what that version changed. A change stays as it is when a later version changed the same value, or when undoing it alone would make the config invalid, and the page says how many such changes it left. The first version cannot be reverted.
- A project's policy starts from a preset, `standard` when none is given, and can override any setting. The presets, from most to least strict, are `strict`, `standard`, and `yolo`, and the Projects page lists them in that order. `strict` makes every merge wait for the owner. `standard`, the default, merges when checks pass and an approving review from the Review job is on the head commit, and stops for changes under `.github/workflows/`. `yolo` merges when checks pass, with no review and no escalation paths. All three revert a factory merge whose checks fail, allow 2 review rounds, cap open factory-filed issues at 5, and need checks to run on a PR; `allowNoChecks` lets a repo without CI merge without them, and `requiredChecks` names checks that must pass on the head and on the merge commit: a bare name is a check run, and `status:<context>` is a commit status.
- The rules every coding thread needs ship in the first message of each implement and review thread: that nobody watches the thread, the task and brief, the branch and what to do when it already exists on origin, not to merge, and the result block. No config version holds them. `instructions.factory` holds only the owner's standing instructions for coding threads, which a deploy writes to Factory Claude's `CLAUDE.md` and Factory Codex's `AGENTS.md` on each worker; it starts empty. A paragraph or line from the coding thread instructions an earlier install copied into version 1 is left out of those files, and the rest stays as typed.
- Each role's own instructions ship with Hephaestus in `templates/roles/`, and no config version holds them, so the owner cannot edit them and an update brings new ones. A role's `persona` holds only the owner's instructions, which the role gets after the shipped ones under the heading "The owner's instructions"; it starts empty. Install once copied the shipped text into version 1, so a persona can hold a copy of an older build's instructions: a paragraph or line that matches one any build shipped is left out, the rest stays as typed, and the Agents page says how many it left out. When the service starts, and every 5 minutes after, Hephaestus checks whether the shipped instructions differ from the ones the factory Hermes root last got, or the MCP tools the roles are offered differ from the ones the factory gateway last loaded; if either does and a version is deployed, it applies the deployed version to the root again, and a failed attempt is tried again at the next check. The improver's `get_config` returns each role's shipped instructions beside the config, read-only.
- The Config page edits the config by tab, and every save creates a version (see [Dashboard](dashboard.md)). Its Versions tab lists versions with their author and state, and a version's page shows its diff and can approve, reject, revert, and deploy it. Deploying publishes the version to the config repo, applies it to the factory Hermes root, and starts a deploy thread on every worker (see [Workers](workers.md)).
- Hephaestus ships starter skills in `templates/skills/`, written for factory threads: `test-first`, `find-root-cause`, `resolve-conflicts`, and `review-pr` for coding threads, `write-issue` for the communicator, and `write-brief` for the lead. Unlike the shipped instructions they are ordinary config, which the owner may edit, unload, or delete. Install puts them in version 1, loaded by their jobs; an imported skill with the same name replaces one. When the service starts, and every 5 minutes after, it compares the starter skills it ships with the deployed version and files a draft from Hephaestus on Proposals that adds the ones the install never had, loaded by their jobs, and brings new text to a starter skill the owner left as install or an earlier draft gave it. A skill the owner edited, deleted, or turned down, and one of their own with the same name, stays as it is. A draft left behind when the owner deployed another version is rejected and filed again on the deployed one.
- The `factory` section sets which skills factory threads load (`threadSkills`), the provider and model of each coding job, the owner's own instance and model that run setup threads on a worker, and the thread limits. `models.claude` holds the Implement job's choice and `models.codex` the Review job's; the keys keep the names of the providers the jobs were tied to before either could choose its own, so a config saved then reads the same. Each may set `provider` to `claude` or `codex`, the factory instance the job runs on, and without it runs on the provider its key names. Both jobs may use the same provider, and a worker needs only the providers the jobs use signed in. Each of those three model choices (`models.claude`, `models.codex`, and `setup`) may also set an `effort` level, which Hephaestus passes to T3 as the provider's effort option when it starts a thread for that role: `effort` for Claude, which accepts low, medium, high, xhigh, max, or ultrathink, and `reasoningEffort` for Codex, which accepts low, medium, high, xhigh, max, or ultra. The setup instance's provider is read from its id: an id that starts with `claude` is a Claude instance and one that starts with `codex` is a Codex instance, and any other id cannot set effort. Validation refuses a level the role's provider does not accept, and a choice that sets effort both as `effort` and in its `options`. A choice without `effort` runs at the model's own default. Each factory thread's record keeps the effort it started with.
- Each project under `projects`, keyed by `owner/repo`, holds its merge `policy` and may hold `skills`: names of skills that factory threads for that project load besides `factory.threadSkills`, on both providers. Threads for other projects do not load them. A project without `skills` loads only `factory.threadSkills`. Validation refuses a name that is not under `skills`, as it does for `threadSkills` and a role's skills, and renaming or deleting a skill on the dashboard renames it in, or removes it from, every project that loads it. A skill meant for the mistakes of one repo belongs in that project's `skills`, where it costs the other projects' threads no context.
- Changes agreed in a chat (author `chat`) go through the same versions, and each is recorded and can be reverted from the chat (see [The factory](factory.md#changes-agreed-in-chat)).
- Every night at 03:00, Hephaestus writes all versions to `~/.hephaestus/backups/` and keeps the newest 14 backups.
- `~/.hephaestus/secrets.json` (mode 600) holds named secrets that config versions refer to by name. Backups leave it out, so secrets must be entered again after a restore.
