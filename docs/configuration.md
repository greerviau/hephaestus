# Configuration

All factory config lives as numbered versions in `~/.hephaestus/state.db`: factory projects and their policies, the planner, lead, and improver roles, the instructions for factory threads, and skills. No repo holds them.

- Every edit creates a draft version with a diff against the version it was built from: the deployed version, or before the first deploy the newest approved one. A draft becomes approved or rejected, an approved version becomes deployed, and the version it replaces becomes superseded. Only a version built from the deployed version can be deployed, so deploying never drops changes made in between.
- Reverting a deployed version creates a draft that restores what that version changed. A change stays as it is when a later version changed the same value, or when undoing it alone would make the config invalid, and the page says how many such changes it left. The first version cannot be reverted.
- A project's policy starts from a preset, `standard` when none is given, and can override any setting. `yolo` merges when checks pass, with no review and no escalation paths. `standard`, the default, also needs an approving review from a different provider on the head commit and stops for changes under `.github/workflows/`. `strict` makes every merge wait for the owner. All three revert a factory merge whose checks fail, allow 2 review rounds, cap open factory-filed issues at 5, and need checks to run on a PR; `allowNoChecks` lets a repo without CI merge without them, and `requiredChecks` names checks that must pass on the head and on the merge commit: a bare name is a check run, and `status:<context>` is a commit status.
- The rules every coding thread needs ship in the first message of each implement and review thread: that nobody watches the thread, the task and brief, the branch and what to do when it already exists on origin, not to merge, and the result block. No config version holds them. `instructions.factory` holds only the owner's standing instructions for coding threads, which a deploy writes to Factory Claude's `CLAUDE.md` and Factory Codex's `AGENTS.md` on each worker; it starts empty. A paragraph or line from the coding thread instructions an earlier install copied into version 1 is left out of those files, and the rest stays as typed.
- Each role's own instructions ship with Hephaestus in `templates/roles/`, and no config version holds them, so the owner cannot edit them and an update brings new ones. A role's `persona` holds only the owner's instructions, which the role gets after the shipped ones under the heading "The owner's instructions"; it starts empty. Install once copied the shipped text into version 1, so a persona can hold a copy of an older build's instructions: a paragraph or line that matches one any build shipped is left out, the rest stays as typed, and the Agents page says how many it left out. When the service starts, and every 5 minutes after, Hephaestus checks whether the shipped instructions differ from the ones the factory Hermes root last got; if they do and a version is deployed, it applies the deployed version to the root again, and a failed attempt is tried again at the next check. The improver's `get_config` returns each role's shipped instructions beside the config, read-only.
- The Config page edits the config by tab, and every save creates a version (see [Dashboard](dashboard.md)). Its Versions tab lists versions with their author and state, and a version's page shows its diff and can approve, reject, revert, and deploy it. Deploying publishes the version to the config repo, applies it to the factory Hermes root, and starts a deploy thread on every worker (see [Workers](workers.md)).
- Hephaestus ships starter skills in `templates/skills/`, written for factory threads: `test-first`, `find-root-cause`, `resolve-conflicts`, and `review-pr` for coding threads, `write-issue` for the planner, and `write-brief` for the lead. Unlike the shipped instructions they are ordinary config, which the owner may edit, unload, or delete. Install puts them in version 1, loaded by their jobs; an imported skill with the same name replaces one. When the service starts with a version deployed, it compares the starter skills it ships with the deployed version and files a draft from Hephaestus on Proposals that adds the ones the version lacks, loaded by their jobs, and brings new text to a starter skill the owner left as an earlier build offered it. A skill the owner edited, or one of their own with the same name, stays as it is. Each text is offered once, so a rejected draft does not come back.
- The `factory` section sets which skills factory threads load (`threadSkills`), the model for each factory instance, the owner's own instance and model that run setup threads on a worker, and the thread limits.
- Every night at 03:00, Hephaestus writes all versions to `~/.hephaestus/backups/` and keeps the newest 14 backups.
- `~/.hephaestus/secrets.json` (mode 600) holds named secrets that config versions refer to by name. Backups leave it out, so secrets must be entered again after a restore.
