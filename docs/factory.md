# The factory

The factory works only on factory projects, the repos listed under `projects` in the deployed config version, and only on issues it may work on.

## Intake

Every two minutes Hephaestus lists each factory project's open issues with `gh`. It records an issue it did not file as external, and an external issue waits for the owner to admit or reject it on the dashboard. An issue a factory role files with `file_issue` is admitted at once, unless the project already has `openIssueCap` factory-filed issues admitted whose card has not started a thread; then it waits for the owner too. Every admitted issue gets a card, and a card on the Hermes board for the lead.

A closed issue leaves the owner's queue and comes back if it is reopened, and closing an admitted issue before any thread starts abandons its card. `gh` lists at most 200 open issues, so an issue missing from a full list is read on its own: 10 such reads per poll split among the projects, with at least one for each, oldest first. The intake reads time out after 30 seconds, so a stalled project delays the next poll by a few minutes at most. Writes to GitHub take no timeout, because one that outlived it might still have happened.

### Attachments

`file_issue` takes an optional `attachments` list of absolute file paths for files a requester sent in a chat, such as an image, which Hermes caches on the Hermes host. Calls without it behave as before.

Only files in the calling role's Hermes media caches can be attached, so no other file on the host can reach GitHub: `cache/images`, `cache/documents`, `cache/audio`, `cache/video`, and `cache/videos` under the role's profile in the factory Hermes root, and the legacy `image_cache`, `document_cache`, `audio_cache`, and `video_cache` there, which Hermes uses in place of the current folders on an install that already has them. A path elsewhere is refused by its name without being read. The path is walked one name at a time from the cache folder, and a symbolic link is refused, as the file or as any folder on the way, even when it points inside the cache. The file is opened without waiting for a writer and must be a regular file, so a named pipe or device is refused at once. Hephaestus cannot tell which request in the cache a file came from, so the limit is the role's media caches and not one request's files. Hephaestus checks every file first: it must exist, be a readable regular file, and be at most 10 MB, and a call takes at most 10 files. Any type is accepted, and URLs are not. A bad file fails the call with an error that names it, and no issue is filed. Otherwise each file is committed through the GitHub API to the branch `hephaestus/attachments` of the target repo, which Hephaestus creates from the default branch when it is missing and uses for nothing else. A file lands at `attachments/<first 16 hex characters of its sha256>/<name>`, so filing the same file again reuses the existing commit, once Hephaestus has read that commit back and found the same bytes there; a file deleted or replaced on the branch since is committed again. Characters in a name outside letters, digits, dot, underscore, and hyphen become underscores. The files are committed before the issue is created, so a failure after that can leave files on the branch with no issue; they are harmless.

The issue body gains an `Attachments` section with a commit-pinned link, the size, and the sha256 of each file, and images (png, jpg, gif, webp, svg) are embedded so they render on the issue. Because the files live on the branch, they outlive the planner's cache.

Hephaestus keeps what each upload returned (path, commit, size, sha256) with the issue it filed, and the implement thread's first message lists each attachment from that record, not from links in the issue text, which anyone can edit and which may hold a link of its own to the same path. An issue Hephaestus stored nothing for gets no such list. The message gives the steps to fetch the exact bytes: `git fetch origin hephaestus/attachments`, then `git show <commit>:<path> > <destination>`. The engineer commits the file into its own branch where the task says; it never pushes to the attachments branch.

## The pipeline

- The lead starts a card with `start_work` and a brief. If the lead has not started an admitted card after `factory.autoStartMinutes` (10 by default; 0 waits for the lead), Hephaestus starts it from the issue. While the factory is paused, an admitted card stays admitted: Hephaestus does not start it, and a `start_work` keeps the lead's brief for when the owner resumes the factory.
- Hephaestus picks the ready worker with the fewest running factory threads and held cards (see below), and the card stays on that worker. It clones the repo there as a T3 project once, then launches the implement thread on Factory Claude in a new worktree on the branch `factory/<install>-card-<id>`, where `<install>` is the first 8 characters of this install's id, so a reinstall's card 1 never reuses the last install's branch. The brief and the issue text go in the first message.
- The implement thread ends with a result block naming its PR and head commit. Only a PR from the card's branch, in the same repo, against the default branch counts. Hephaestus then launches a review thread on Factory Codex for that exact commit. When the reviewer asks for changes and the policy's `maxReviewRounds` remain, the findings go back to the implement thread.
- The card is escalated to the lead when the thread fails, asks a question, gives no valid result block, or runs out of review rounds. The lead restarts it with `start_work`, or escalates it to the owner with `escalate`.
- A thread that stops on its provider's usage limit is not a failure, and its card is not escalated. The card keeps its stage and says it waits for the limit to reset. When T3 snoozes the thread until the reset, Hephaestus gives T3 five minutes after the reset to resume it, then follows the resumed run. When T3 reports no reset time, or does not resume the thread, Hephaestus sends the thread a message to continue, every 30 minutes until a run gets past the limit. It reads T3 again right before it sends, and a thread T3 resumed meanwhile is followed instead. Hephaestus tells runs apart by the run T3 reports for each item, so a resumed run is never taken for the limited one, and a resumed run that ends with no output of its own goes to the lead. Only the provider's own usage-limit wording counts, in a thread's error or in a short completed reply; another service's rate limit, such as GitHub's, goes to the lead.
- Before each thread start, and before each message that resumes a thread, Hephaestus checks the pause switch, that the worker is ready, and the limits in `factory.limits`: running factory threads per worker and overall, and thread starts per UTC day. A card with the lead, a card waiting for a usage limit to reset, and a card whose thread ended with a result Hephaestus has not acted on yet, each hold a slot of the running-thread limits against new thread starts, since their work is not finished; a message that continues a card's own thread does not wait on them. A card with the owner holds none. A card that cannot start says why, and counts the held cards by why each holds a slot.

## The merge gate

Hephaestus merges a PR itself, squashing it, only when the project's policy allows it:

- Every check on the head commit passed, at least one ran unless the policy sets `allowNoChecks`, and every check named in the policy's `requiredChecks` ran and passed. Hephaestus reads every check run and status through `gh`'s paginated API, so the gate works without branch protection. It waits three minutes after a new head so slow checks can register, and a head still waiting for checks after an hour goes to the owner.
- Unless the policy is `yolo`, the other provider's review approved exactly that head commit.
- No changed file, including the old name of a renamed one, matches an escalation path, unless the owner approved that head on the dashboard.
- The policy allows auto-merge and does not have the owner approve every merge.

Otherwise the card is escalated with the reason: to the lead for failing checks or a missing review, and to the owner for escalation paths and owner approval. Hephaestus merges through GitHub's merge API, which answers with the merge commit, and puts `Merged by Hephaestus for card <id>.` in the squash commit. A PR someone else merged first is never taken for its own, and a merge whose reply was lost is recognized by that line. When GitHub cannot be read back to tell, the card goes to the owner. A PR that conflicts with its base branch, by GitHub's refusal or its mergeable state, goes back to the implement thread to bring in the base branch, as one more review round, or to the lead once `maxReviewRounds` is spent; the new head goes through the gate again. A conflicting revert PR goes to the owner. When GitHub refuses the merge with a 405 or 409 that is not a conflict, such as a branch that must be up to date, a required human review, or a merge queue, Hephaestus tries once more, and when the same head is refused again the card goes to the owner with GitHub's message, so the owner can change the rule or merge by hand; a revert PR is handled the same way. Network errors and server errors keep retrying in Merging. Agents are told never to merge. A factory PR merged by anything else ends its card, flagged, and Hephaestus never validates or reverts that merge.

## Validation and revert

After a merge, Hephaestus watches the merge commit's checks on the default branch. Every check that ran on the PR's head must run and finish there too. When one has not after an hour, the owner is notified and validation goes on, so a late failure still reverts. When they pass, the card is done. When they fail and the policy has `autoRevert`, Hephaestus opens GitHub's revert PR and merges it under the same gate, with its own review. A revert PR that has not merged an hour after its head appeared goes to the owner, even while its review waits for a usage limit to reset. A new head on the revert PR, or a merge of it, drops that review along with its usage-limit wait. It then reopens the issue, notifies the owner, and starts the card again from a new implement thread that is told about the revert.

## MCP server

The factory profiles reach Hephaestus through an MCP server on `127.0.0.1`, on the port after the dashboard's. Each profile has its own bearer token, kept in `~/.hephaestus/secrets.json` and in the profile's `.env`, and each role gets only its tools:

| Role     | Tools                                                                                                      |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| planner  | `file_issue`, `get_status`, `list_cards`, `read_thread`, the stats tools below, and the change tools below |
| lead     | `start_work`, `escalate`, `file_issue`, `get_status`, `list_cards`, `read_thread`                          |
| improver | `propose_version`, `get_config`, `get_status`, `list_cards`, `list_threads`, `read_thread`                 |

The planner is the chat agent. It is a general communicator: it talks, answers questions about the factory from `get_status`, `list_cards`, and `read_thread` (a card carries `merged_at`, its recorded merge time, which is not its last update), and uses `file_issue` only when the user asks for work. Besides `file_issue` its only write tools are the change tools below.

Every call is recorded with the calling role, including calls to a tool the role does not have. `propose_version` creates a draft config version authored by the improver, with the factory threads it cites as evidence; it changes nothing until the owner approves it.

### Changes agreed in chat

The profile that talks to people in chat can change the factory's own skills, instructions, personas, and settings, but only after the person agrees in that conversation. The allowlist is in `src/factory/chat-changes.ts`, and the tools' descriptions, which carry the flow the agent follows, are in `src/factory/chat-change-tools.ts`. Its change tools are `list_targets`, `read_target`, `propose_change`, `apply_change`, `decline_change`, `list_changes`, and `revert_change`.

- Only an allowlist can change: a file in a skill (`skill:<skill>/<file>`, an existing file or a new one), an instruction (`instruction:<name>`), a role's persona (`persona:<role>`, the owner's own instructions for the role, never the shipped ones), and the settings `autoStartMinutes`, `threadSkills`, `models.claude`, `models.codex`, `limits.threadsPerWorker`, `limits.threads`, and `limits.startsPerDay` (`setting:<name>`, as JSON). Projects and their policies, the setup instance, a role's skills and cron jobs, and everything outside the config are refused, so the merge gate is never loosened from chat. A skill file whose name says it holds a secret (`.env`, `secrets`, `credentials`, `token`, `*.pem`, `*.key`, and similar) is refused, and so is any text that looks like a credential, such as a GitHub or API token, a private key, or a `password=` line. The refusal never repeats the text, and the call log keeps only the size of proposed text.
- `propose_change` takes the whole new text and checks it before it returns: the size, the format (a setting must be JSON, a `SKILL.md` frontmatter block must close and hold `key: value` lines, a `.json` file must parse), and the config's own rules. It writes nothing to the config and returns the exact diff for the agent to post in the chat. A proposal that is declined, ignored, or older than 24 hours is never applied.
- `apply_change` needs the proposal's conversation and the person's approving message. It refuses another conversation's approval, a change already applied or declined, and an approval less than 5 seconds after the proposal, which is too soon for a person to have read the diff. It builds a new config version from the deployed version with the one target changed, checks it again, approves it as author `chat`, and deploys it. A target that changed since the proposal fails the change, so an edit made on the dashboard is never overwritten. The tool reports any validation or deploy error, and the record keeps it.
- Every change is a row with its target, summary, conversation, the approval, the config version, and when it was proposed and applied, and its before and after text. The versions appear on the Settings page with author `chat`.
- `revert_change` puts an applied change's target back as it was, as a new version, when the person asks for it. It is refused when the target has changed since, because reverting would overwrite the later edit.
- Hephaestus reads the deployed version live, so `autoStartMinutes`, the limits, and the models apply to the next card or thread after the deploy, with no restart. Skills for factory threads reach each worker with the deploy. A role's persona, and the skills a role loads, are written to its Hermes profile at deploy, and the deploy does not restart the factory gateway, so a conversation already running may keep its earlier instructions until Hermes reloads the profile.

### Stats tools

The chat agent answers questions about the factory with three read-only tools. Each returns the numbers and a `report` of bullet lines with no tables, and takes `window` (hours or days, such as `24h`, `7d`, or `30d`; the default is `7d`, and `24h` for host errors).

- `get_factory_stats` (also `repo` to limit it to one project) gives cards by stage as they stand now, cards that reached Done in the window and per day, cycle time from the first thread to Done (median and 90th percentile), review rounds of those cards, escalations with their targets and reasons, and held issues per project.
- `get_usage_stats` (also `repo`) gives the engineer and reviewer threads started in the window, with token counts and cost by role, model, and card. Hephaestus does not capture usage from T3 yet, so a thread has token counts and a cost only when something recorded them, and the report never estimates either. When none is recorded, the report says tokens and cost are not recorded and still gives thread counts. A total that covers only some threads says how many.
- `get_host_health` gives CPU cores and load average, memory, disk, host uptime, the state of the Hephaestus and Hermes gateway services as systemd reports it, each worker's config version and problem, and the failed tool calls, worker tasks, and thread launches recorded in the window.

When data is missing the report says so, and the chat agent is told never to fill a gap with a number it did not get from a tool.
